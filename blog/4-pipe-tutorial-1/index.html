Pipe Syntax Tutorial: Lesson 1

Published: 2025 Dec 29
Written by: Michael

Introduction

I have been using Google’s pipe query syntax (henceforth just “pipe syntax”) as my daily driver in work for about a year now. I find myself a lot more productive when developing queries, and find it a lot easier to underestand queries that I wrote several months ago when reviewing them.

I want to start documenting my learnings and experience in the form of hands-on exercises that hopefully readers can follow along with.

Any and all feedback is welcome at any time. Please email them to: michael[at]fullstackdata.dev

Prerequisites

I will assume the reader is familiar with basic SQL concepts (e.g. joins, aggregation, CTEs, structs, arrays) and is willing to reference Google’s SQL docs or other reading materials as needed. Most importantly, I will assume the reader is not a complete novice in data modelling using SQL. After all, the intended audience for the tutorial’s full scope are analysts/engineers that find conventional SQL unnecessarily tedious to develop and maintain for complex data needs. There’s not much point in learning pipe syntax if all you need is to count or sum over a column.

Some readers may find that the difficulty of the exercises ramp up pretty quickly. I expect this to be the case since I need non-trivial (sometimes complex) examples for data modelling exercises to demonstrate some more powerful uses of Pipe syntax. Furthermore, working with an unfamiliar dataset almost always comes at the cost of additional headspace required, so don’t be discouraged and reread the lessons at your own pace.

Setting up a BigQuery sandbox

Since this series of lessons is intended to be hands-on, I encourage the reader to setup a sandbox in BigQuery to play around with the queries or even attempt to develop the query before reading the sample solution. See Google’s guide here on setting up a sandbox.

We will be querying Google’s public dataset bigquery-public-data.google_analytics_sample throughout the lessons. To test you have setup your sandbox correctly, run the following query in the BigQuery console and check that the query returns 2556.

FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> AGGREGATE
    SUM(totals.visits) AS total_visits,

While you can choose to learn more about the dataset in Google’s guide, I don’t expect you to, and will provide my interpretation of the data where needed.

Exercises

Exercises will start with a brief section explaining what new feature/operator in Pipe syntax we’ll be introducing. They will then be followed by the task (i.e. “the business question”), the expected result, and a sample solution. All exercises query the same table as the setup check above, where each row is one session (a visit to the Google Merchandise Store).

Exercise 1: Conversion rate by device

Lesson

A pipe syntax query starts with FROM. FROM table on its own is already a complete query, which returns every column of the table, like SELECT * FROM table does.

Each |> (a “pipe”) passes the table produced so far to the next operator. Every operator takes a table and produces a new table, so the query reads from top to bottom in the order it runs.

First up is |> AGGREGATE, which is the pipe syntax version of a SELECT ... GROUP BY query in standard SQL.

FROM table
|> AGGREGATE
    COUNT(1) AS metric_1, -- This should be pretty familiar
    -- All aggregate functions come *before* GROUP BY
  GROUP BY
    -- All grouping dimensions come *after* GROUP BY
    dimension_1,
    CAST(dimension_2 AS STRING) AS new_dimension, -- You can create new dimensions just like usual. Don't go crazy though!
    dimension_3 DESC, -- You can add sorting logic too. But use |> ORDER BY for multi-column sorts for readability.
    dimension_4, -- Optional trailing comma, yay!

Next up is |> EXTEND, which adds new columns to the end of the table, like SELECT *, ... in standard SQL.

FROM table
|> EXTEND
    metric_1 / metric_2 AS ratio, -- Can use any column from an earlier step
    UPPER(dimension_1) AS dimension_1_upper, -- Add as many columns as you like

Finally, |> ORDER BY sorts the table, the same as ORDER BY in standard SQL.

FROM table
|> ORDER BY
    metric_1 DESC,
    dimension_1, -- Trailing comma here too

Here’s an example query tying everything together: count sessions and hits by traffic medium, compute the average hits per session, and order by highest session count first.

FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> AGGREGATE
    COUNT(*) AS sessions,
    SUM(totals.hits) AS hits,
  GROUP BY
    trafficSource.medium AS medium
|> EXTEND hits / sessions AS hits_per_session
|> ORDER BY sessions DESC

Task

For each device category (device.deviceCategory), find:

  • the number of sessions,
  • the total number of pageviews (totals.pageviews),
  • the number of converting sessions, which are sessions with at least one transaction (totals.transactions > 0),
  • the conversion rate, which is converting sessions divided by sessions.

Sort the result by the number of sessions, highest first.

Expected result below:

device_categorysessionspageviewsconverting_sessionsconversion_rate
desktop17428329410.0235
mobile725233220.0028
tablet8927800.0

 

Sample solution
FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> AGGREGATE
   COUNT(*) AS sessions,
   SUM(totals.pageviews) AS pageviews,
   COUNTIF(totals.transactions > 0) AS converting_sessions,
 GROUP BY
   device.deviceCategory AS device_category
|> EXTEND SAFE_DIVIDE(converting_sessions, sessions) AS conversion_rate
|> ORDER BY sessions DESC

Discussion

In standard SQL, the conversion rate would need either a second CTE or a repeat of both aggregate expressions inside SAFE_DIVIDE. In pipe syntax, |> EXTEND can refer to the aggregated columns by name in the very next step.

Exercise 2: Conversion rate by channel, for engaged sessions

Lesson

This time we only need |> WHERE, which filters rows, the same as WHERE in standard SQL. The difference is that it can appear anywhere in the query, as many times as you need, so pipe syntax doesn’t need HAVING.

FROM table
|> WHERE dimension_1 = 'x' -- Filters the rows of the table, like WHERE in standard SQL
|> AGGREGATE
    COUNT(1) AS metric_1,
  GROUP BY
    dimension_2,
|> WHERE metric_1 > 100 -- Filters the aggregated rows, like HAVING in standard SQL

Here’s an example query: filter for mobile sessions, count them by continent, and keep continents with at least 100 sessions.

FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> WHERE device.isMobile
|> AGGREGATE
    COUNT(*) AS sessions,
  GROUP BY
    geoNetwork.continent AS continent
|> WHERE sessions >= 100

Task

Only consider sessions with more than one pageview. For each channel (channelGrouping), find the number of sessions, the number of converting sessions and the conversion rate rounded to 4 decimal places. Only keep channels with at least 20 sessions, and sort the result by conversion rate, highest first.

Expected result below:

channelGroupingsessionsconverting_sessionsconversion_rate
Referral329270.0821

Paid Search4710.0213
Organic Search62960.0095

Sample solution
FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> WHERE totals.pageviews > 1
|> AGGREGATE
   COUNT(*) AS sessions,
   COUNTIF(totals.transactions > 0) AS converting_sessions,
 GROUP BY
   channelGrouping
-- Order of WHERE/EXTEND below don't matter
|> WHERE sessions >= 20
|> EXTEND ROUND(SAFE_DIVIDE(converting_sessions, sessions), 4) AS conversion_rate
|> ORDER BY conversion_rate DESC

Discussion

Every line that changes the number of rows starts with |> WHERE or |> AGGREGATE, and they run from top to bottom. As an extra exercise, write the same query in standard SQL. Notice that WHERE, GROUP BY and HAVING are spread around the SELECT list, and the reader has to remember the order in which SQL applies them.

Exercise 3: Sessions by hour of day

Lesson

First up is |> SELECT, which keeps only the columns you list, like the SELECT list in standard SQL.

FROM table
|> SELECT
    dimension_1,
    struct_1.field_1, -- The new column is named after the field, i.e. field_1
    metric_1 * 100 AS metric_1_pct, -- Expressions and aliases work as usual

Next up is |> SET, which replaces the values of existing columns, like SELECT * REPLACE (...) in standard SQL. The syntax is no longer new_definition AS column_name. Instead, write column_name = new_definition.

FROM table
|> SET
    metric_1 = IFNULL(metric_1, 0),
    dimension_1 = UPPER(dimension_1),
    -- new_column = 1, -- Error! SET only replaces existing columns. Use EXTEND to add new ones.

Then there’s |> DROP, which removes columns, like SELECT * EXCEPT (...) in standard SQL. You won’t need it for this exercise, but it often appears next to SET.

FROM table
|> DROP
    dimension_1,
    metric_1,

Finally, |> LIMIT keeps only the first few rows, the same as LIMIT in standard SQL.

Here’s an example query tying everything together: keep three columns, replace missing pageviews with 0, drop visitNumber, and show the first 3 rows.

FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> SELECT visitId, visitNumber, totals.pageviews
|> SET pageviews = IFNULL(pageviews, 0)
|> DROP visitNumber
|> LIMIT 3

Task

visitStartTime is the start of the session in seconds since the Unix epoch. Convert it to a timestamp, find the hour of day in Los Angeles time ('America/Los_Angeles'), and count the sessions and pageviews in each hour. Sort the result by hour, earliest first.

Expected result below (excerpt):

local_hoursessionspageviews

169179
273168
………

Sample solution
FROM `bigquery-public-data.google_analytics_sample.ga_sessions_20170801`
|> SELECT visitStartTime, totals.pageviews
|> SET visitStartTime = TIMESTAMP_SECONDS(visitStartTime)
|> EXTEND EXTRACT(HOUR FROM visitStartTime AT TIME ZONE 'America/Los_Angeles') AS local_hour
|> AGGREGATE
   COUNT(*) AS sessions,
   SUM(pageviews) AS pageviews,
 GROUP BY
   local_hour
|> ORDER BY local_hour

Discussion

Each step uses the result of the step before it: EXTEND reads the timestamp that SET just created. In standard SQL, each step would need its own CTE with SELECT * REPLACE (...), or the expressions would have to be nested inside each other.

Pipe syntax also makes debugging easier. To see the data at any step, comment out every line below it and run the query. For example, comment out the last two lines to check local_hour before aggregating.
